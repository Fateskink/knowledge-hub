# Mô Hình MVC: Model-View-Controller Giải Thích Chi Tiết

MVC (Model-View-Controller) là một trong những mô hình kiến trúc phần mềm lâu đời và phổ biến nhất trong lịch sử phát triển phần mềm. Dù bạn đang xây dựng ứng dụng web với Express.js, Django hay Spring, khả năng cao bạn đã hoặc sẽ gặp MVC. Bài viết này sẽ giải thích chi tiết MVC là gì, cách nó hoạt động, và khi nào nên (hoặc không nên) sử dụng nó.

## MVC là gì?

MVC là viết tắt của **Model-View-Controller** — một mô hình kiến trúc chia ứng dụng thành ba thành phần chính, mỗi thành phần đảm nhận một trách nhiệm riêng biệt:

- **Model**: Quản lý dữ liệu và business logic
- **View**: Hiển thị giao diện người dùng
- **Controller**: Điều phối giữa Model và View

<Callout type="info">MVC được phát minh bởi Trygve Reenskaug vào năm 1979 tại Xerox PARC, ban đầu dành cho ngôn ngữ Smalltalk. Đây là một trong những mô hình kiến trúc phần mềm đầu tiên được đặt tên chính thức và vẫn còn được sử dụng rộng rãi sau hơn 45 năm.</Callout>

## Ba thành phần của MVC

### Model — Trái tim của ứng dụng

Model chịu trách nhiệm quản lý **dữ liệu**, **trạng thái** và **business logic** của ứng dụng. Model không biết gì về View hay Controller — nó hoàn toàn độc lập.

Các nhiệm vụ chính của Model:
- Truy xuất và lưu trữ dữ liệu (database, API, file)
- Xác thực dữ liệu (validation)
- Thực hiện business logic (tính toán, xử lý nghiệp vụ)
- Thông báo cho View khi dữ liệu thay đổi (trong mô hình Observer)

### View — Giao diện người dùng

View chịu trách nhiệm **hiển thị dữ liệu** từ Model cho người dùng. View không chứa business logic mà chỉ tập trung vào việc trình bày.

Các nhiệm vụ chính của View:
- Render HTML, CSS, template
- Hiển thị dữ liệu từ Model
- Nhận tương tác từ người dùng và chuyển cho Controller
- Cập nhật giao diện khi Model thay đổi

### Controller — Bộ điều phối

Controller đóng vai trò **trung gian** giữa Model và View. Nó nhận yêu cầu từ người dùng (thông qua View), xử lý logic điều hướng, gọi Model để thao tác dữ liệu, và chọn View phù hợp để hiển thị kết quả.

Các nhiệm vụ chính của Controller:
- Nhận và xử lý HTTP request (trong ứng dụng web)
- Gọi Model để đọc/ghi dữ liệu
- Chọn View để render kết quả
- Xử lý luồng điều hướng (routing)

## Luồng dữ liệu trong MVC

<Diagram chart="graph LR\n    U[Người dùng] -->|1. Gửi request| C[Controller]\n    C -->|2. Yêu cầu dữ liệu| M[Model]\n    M -->|3. Trả về dữ liệu| C\n    C -->|4. Gửi dữ liệu| V[View]\n    V -->|5. Hiển thị| U" />

Luồng xử lý điển hình trong một ứng dụng web MVC:

1. **Người dùng** gửi request (ví dụ: truy cập `/products/123`)
2. **Controller** nhận request, xác định hành động cần thực hiện
3. **Controller** gọi **Model** để lấy dữ liệu sản phẩm có ID 123
4. **Model** truy vấn database, trả về đối tượng Product
5. **Controller** truyền dữ liệu cho **View** phù hợp
6. **View** render HTML với dữ liệu sản phẩm và trả về cho người dùng

## Ví dụ thực tế: Express.js MVC

Dưới đây là cấu trúc một ứng dụng Express.js theo mô hình MVC:

```
project/
├── models/
│   └── product.model.js
├── views/
│   └── product.ejs
├── controllers/
│   └── product.controller.js
├── routes/
│   └── product.routes.js
└── app.js
```

### Model — product.model.js

```javascript
// models/product.model.js
const db = require('../config/database');

class Product {
  static async findById(id) {
    const result = await db.query(
      'SELECT * FROM products WHERE id = $1',
      [id]
    );
    return result.rows[0];
  }

  static async findAll({ category, limit = 20 }) {
    let query = 'SELECT * FROM products';
    const params = [];

    if (category) {
      query += ' WHERE category = $1';
      params.push(category);
    }

    query += ` LIMIT ${limit}`;
    const result = await db.query(query, params);
    return result.rows;
  }

  static async create(data) {
    const { name, price, description } = data;
    // Validation - business logic nằm trong Model
    if (price < 0) throw new Error('Giá không được âm');

    const result = await db.query(
      'INSERT INTO products (name, price, description) VALUES ($1, $2, $3) RETURNING *',
      [name, price, description]
    );
    return result.rows[0];
  }
}

module.exports = Product;
```

### Controller — product.controller.js

```javascript
// controllers/product.controller.js
const Product = require('../models/product.model');

const productController = {
  async show(req, res) {
    try {
      const product = await Product.findById(req.params.id);
      if (!product) {
        return res.status(404).render('error', { message: 'Không tìm thấy sản phẩm' });
      }
      res.render('product', { product });
    } catch (error) {
      res.status(500).render('error', { message: 'Lỗi hệ thống' });
    }
  },

  async index(req, res) {
    const products = await Product.findAll({
      category: req.query.category,
    });
    res.render('products', { products });
  },

  async create(req, res) {
    try {
      const product = await Product.create(req.body);
      res.redirect(`/products/${product.id}`);
    } catch (error) {
      res.status(400).render('productForm', { error: error.message });
    }
  },
};

module.exports = productController;
```

### View — product.ejs

```html
<!-- views/product.ejs -->
<div class="product-detail">
  <h1><%= product.name %></h1>
  <p class="price"><%= product.price.toLocaleString() %> VNĐ</p>
  <p class="description"><%= product.description %></p>
  <a href="/products">← Quay lại danh sách</a>
</div>
```

<Callout type="tip">Trong Express.js, file routes đóng vai trò ánh xạ URL đến Controller. Nhiều framework khác (như Rails, Django) tích hợp sẵn routing trong cấu hình, nhưng nguyên lý là giống nhau.</Callout>

## MVC trong các framework phổ biến

Các framework lớn đều áp dụng MVC hoặc biến thể của nó:

- **Ruby on Rails**: MVC thuần túy — là framework phổ biến hóa MVC cho web
- **Django (Python)**: Sử dụng biến thể **MVT** (Model-View-Template), trong đó View của Django tương đương Controller, và Template tương đương View
- **Spring MVC (Java)**: MVC với annotation-based routing và dependency injection
- **ASP.NET MVC (C#)**: MVC với convention over configuration
- **Laravel (PHP)**: MVC với Eloquent ORM và Blade template

<Callout type="warning">Django gọi tên khác nhưng bản chất giống MVC. View trong Django thực chất là Controller, còn Template mới là View. Đừng nhầm lẫn khi chuyển đổi giữa các framework.</Callout>

## Các biến thể: MVP và MVVM

Theo thời gian, MVC đã phát triển thành nhiều biến thể để phù hợp với các nền tảng và yêu cầu khác nhau.

### MVP — Model-View-Presenter

<Diagram chart="graph LR\n    V[View] <-->|Tương tác| P[Presenter]\n    P <-->|Dữ liệu| M[Model]\n    V -.->|Hiển thị| U[Người dùng]" />

Trong MVP, **Presenter** thay thế Controller. Điểm khác biệt chính:
- View chủ động hơn — nó có interface mà Presenter gọi
- Presenter giữ reference đến View thông qua interface
- Không có kết nối trực tiếp giữa Model và View
- Phổ biến trong Android (trước khi có MVVM) và WinForms

### MVVM — Model-View-ViewModel

<Diagram chart="graph LR\n    V[View] -->|Data Binding| VM[ViewModel]\n    VM -->|Cập nhật| M[Model]\n    M -->|Thông báo| VM\n    VM -->|Tự động cập nhật| V" />

Trong MVVM, **ViewModel** thay thế Controller. Điểm khác biệt chính:
- Sử dụng **data binding** hai chiều giữa View và ViewModel
- ViewModel không biết về View cụ thể
- View tự động cập nhật khi ViewModel thay đổi (reactive)
- Phổ biến trong WPF, Xamarin, Angular, Vue.js, SwiftUI

## Ưu điểm và nhược điểm của MVC

### Ưu điểm

- **Tách biệt mối quan tâm (Separation of Concerns)**: Mỗi thành phần có trách nhiệm rõ ràng, code dễ hiểu và bảo trì
- **Phát triển song song**: Frontend và backend developer có thể làm việc đồng thời trên View và Model
- **Tái sử dụng**: Model có thể dùng chung cho nhiều View (web, mobile, API)
- **Dễ test**: Model có thể unit test độc lập mà không cần UI
- **Cộng đồng lớn**: Hầu hết developer đều quen thuộc với MVC

### Nhược điểm

- **Controller phình to (Fat Controller)**: Khi ứng dụng phát triển, Controller dễ trở thành nơi chứa quá nhiều logic
- **Liên kết chặt giữa Controller và View**: Khó tái sử dụng Controller cho các View khác nhau
- **Không phù hợp cho UI phức tạp**: Các ứng dụng SPA với state phức tạp cần giải pháp mạnh hơn (MVVM, Flux/Redux)
- **Boilerplate nhiều**: Mỗi feature cần tạo đủ bộ ba Model-View-Controller

<Callout type="danger">Tránh đặt business logic vào Controller (Fat Controller anti-pattern). Controller chỉ nên điều phối — gọi Model để xử lý nghiệp vụ, rồi chọn View để hiển thị. Nếu Controller quá dài, hãy tách logic ra thành Service layer.</Callout>

## Khi nào nên dùng MVC?

**Phù hợp khi:**
- Xây dựng ứng dụng web server-side rendering (SSR)
- Ứng dụng CRUD với luồng dữ liệu rõ ràng
- Team quen thuộc với mô hình MVC
- Dự án vừa và nhỏ cần cấu trúc cơ bản

**Không phù hợp khi:**
- Ứng dụng SPA phức tạp với nhiều state — hãy dùng MVVM hoặc Flux/Redux
- Hệ thống microservices phức tạp — hãy xem xét DDD, Clean Architecture
- Ứng dụng real-time với luồng dữ liệu phức tạp — hãy dùng Event-Driven Architecture
- Dự án rất nhỏ (landing page, script) — MVC là quá mức cần thiết

## Tổng kết

MVC là nền tảng kiến trúc mà mọi developer cần nắm vững. Dù bạn sử dụng framework nào, hiểu được nguyên lý tách biệt Model, View và Controller sẽ giúp bạn viết code có cấu trúc tốt hơn. Từ MVC, bạn có thể tiến đến các mô hình nâng cao hơn như MVP, MVVM, hay Clean Architecture — tất cả đều xây dựng trên cùng một triết lý: **tách biệt mối quan tâm**.

<Callout type="tip">Bước tiếp theo: Tìm hiểu về Domain-Driven Design (DDD) để biết cách tổ chức business logic phức tạp trong Model layer, đặc biệt khi ứng dụng của bạn vượt qua quy mô mà MVC đơn giản có thể xử lý.</Callout>
