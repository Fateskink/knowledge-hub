## Configuration Overview

Claude Code is designed to work well out of the box, but its true power emerges when you customize it to match your workflow, your team's conventions, and your project's unique requirements. Configuration happens at multiple levels, each with a different scope and purpose.

<Diagram chart="graph TD\n    A[Configuration Layers] --> B[Global Settings]\n    A --> C[Project Settings]\n    A --> D[CLAUDE.md Memory]\n    A --> E[Permission Profiles]\n    A --> F[Environment Variables]\n    B --> B1[~/.claude/settings.json]\n    C --> C1[.claude/settings.json]\n    D --> D1[Project CLAUDE.md]\n    D --> D2[User ~/.claude/CLAUDE.md]\n    E --> E1[Built-in Profiles]\n    E --> E2[Custom Profiles]\n    F --> F1[API Keys, Model Config]" />

## Settings Files

Claude Code uses JSON settings files at two levels:

### Global Settings (`~/.claude/settings.json`)

These apply to every Claude Code session across all projects:

```json
{
  "model": "claude-sonnet-4-20250514",
  "smallModel": "claude-haiku-4-5-20241022",
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "WebSearch"
    ],
    "deny": []
  },
  "mcpServers": {},
  "hooks": {}
}
```

### Project Settings (`.claude/settings.json`)

These apply only to the current project and are shared with your team via version control:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npx tsc --noEmit)",
      "Bash(npx eslint)"
    ],
    "deny": [
      "Bash(rm -rf)",
      "Bash(git push --force)"
    ]
  },
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": {
        "POSTGRES_CONNECTION_STRING": ""
      }
    }
  }
}
```

<Callout type="info">
Project settings merge with global settings. Project-level permissions can add restrictions but cannot override global denials. This ensures safety even when working with shared project configurations.
</Callout>

## CLAUDE.md: The Memory System

CLAUDE.md is one of Claude Code's most distinctive features. It is a markdown file that Claude reads at the start of every session to understand your project's context, conventions, and preferences. Think of it as an onboarding document for your AI pair programmer.

### How CLAUDE.md Works

When Claude Code starts a session, it automatically reads CLAUDE.md files from several locations, in order of precedence:

1. **`~/.claude/CLAUDE.md`** - Personal preferences that apply everywhere
2. **`CLAUDE.md`** in the project root - Project-level context
3. **`CLAUDE.md`** in subdirectories - Directory-specific context (read when working in those directories)

### Writing an Effective CLAUDE.md

A good CLAUDE.md file covers the essential information Claude needs to work effectively in your project:

```markdown
# Project: E-Commerce Platform

## Tech Stack
- **Framework**: Next.js 15 with App Router
- **Language**: TypeScript (strict mode)
- **Database**: PostgreSQL with Drizzle ORM
- **Styling**: Tailwind CSS v4
- **Testing**: Vitest + React Testing Library
- **Package Manager**: pnpm

## Project Structure
- `src/app/` - Next.js app router pages
- `src/components/` - Reusable React components
- `src/lib/` - Utility functions and shared logic
- `src/db/` - Database schema and migrations
- `src/api/` - API route handlers

## Coding Conventions
- Use functional components with hooks (no class components)
- Prefer named exports over default exports
- Use absolute imports with `@/` prefix
- Error handling: use custom AppError class from `@/lib/errors`
- All API responses use the envelope format: `{ data, error, meta }`

## Commands
- `pnpm dev` - Start development server
- `pnpm test` - Run all tests
- `pnpm test:watch` - Run tests in watch mode
- `pnpm lint` - Run ESLint
- `pnpm db:migrate` - Run database migrations
- `pnpm db:seed` - Seed the database

## Important Notes
- Never commit .env files
- Always use parameterized queries (no string interpolation in SQL)
- All user-facing strings must use i18n keys from `src/i18n/`
```

<Callout type="tip">
Keep your CLAUDE.md concise and focused on information that Claude needs to make correct decisions. Avoid documenting things that are obvious from the code itself. Focus on conventions, gotchas, and non-obvious project details.
</Callout>

### Managing CLAUDE.md In-Session

You can view and edit CLAUDE.md files directly from a Claude Code session:

```
/memory                     # View current CLAUDE.md contents
/memory edit                # Open CLAUDE.md for editing
```

Claude can also update its own memory. When you tell Claude something important about the project, it may ask to save that information to CLAUDE.md for future sessions:

```
> Our API always requires X-Request-ID headers for tracing

Claude: I'll remember that. Would you like me to add this to CLAUDE.md
so I remember in future sessions?
```

## Permission Profiles

Permission profiles control what Claude Code is allowed to do without asking for confirmation. This is crucial for balancing productivity with safety.

### Built-in Profiles

  rows={[
    ["Default", "Ask before writes and commands", "General development, unfamiliar codebases"],
    ["Permissive", "Auto-approve most operations", "Trusted projects, experienced users"],
    ["Read-only", "No writes or command execution", "Code review, exploration, Q&A"]
  ]}
/>

### Using Profiles

```bash
# Launch with a specific profile
claude --profile permissive

# Check current permissions
/permissions
```

### Custom Permission Rules

Fine-grained control over specific commands:

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Bash(npm test)",
      "Bash(npm run lint)",
      "Bash(git status)",
      "Bash(git diff)",
      "Bash(git log)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force)",
      "Bash(curl * | sh)",
      "Bash(sudo *)"
    ]
  }
}
```

<Callout type="warning">
Permission rules use pattern matching. The pattern `Bash(npm test)` allows exactly that command. Use wildcards carefully: `Bash(npm *)` would allow any npm command, including potentially destructive ones like `npm unpublish`.
</Callout>

## Environment Variables

Several environment variables control Claude Code's behavior:

```bash
# Authentication
export ANTHROPIC_API_KEY=sk-ant-...

# Model override
export CLAUDE_MODEL=claude-opus-4-20250918

# Custom API endpoint (for enterprise proxies)
export ANTHROPIC_BASE_URL=https://proxy.company.com/v1

# Disable telemetry
export CLAUDE_CODE_DISABLE_TELEMETRY=1

# Set max tokens for output
export CLAUDE_MAX_TOKENS=16384
```

Add these to your shell profile (`~/.zshrc` or `~/.bashrc`) for persistent configuration.

## IDE Integrations

While Claude Code is a terminal-native tool, it integrates with popular IDEs for a richer experience.

### VS Code Extension

The Claude Code VS Code extension brings the CLI experience into your editor:

```bash
# Install the extension
code --install-extension anthropic.claude-code
```

Key features of the VS Code integration:

- **Side panel**: Chat with Claude Code without leaving your editor
- **File context**: Automatically include open files in the conversation
- **Inline diffs**: See proposed changes as inline diffs in the editor
- **Terminal integration**: Claude Code commands run in the integrated terminal

<Diagram chart="graph LR\n    A[VS Code Editor] --> B[Claude Code Extension]\n    B --> C[Side Panel Chat]\n    B --> D[Inline Diff View]\n    B --> E[Integrated Terminal]\n    C --> F[Claude Code Agent]\n    D --> F\n    E --> F" />

### JetBrains Integration

Claude Code works with JetBrains IDEs (IntelliJ, WebStorm, PyCharm) through the terminal:

```bash
# Open the IDE's integrated terminal
# Navigate to your project
# Run Claude Code as usual
claude
```

While there is no dedicated JetBrains plugin yet, the terminal-based workflow integrates naturally with JetBrains' built-in terminal.

### Vim/Neovim

For terminal-based editors, Claude Code works seamlessly. You can run it in a split terminal or use it alongside your editor:

```bash
# In a tmux or screen session
# Pane 1: Your editor
vim src/app.ts

# Pane 2: Claude Code
claude
```

## Advanced Configuration

### Custom System Prompts

For specialized use cases, you can provide additional system prompt instructions:

```bash
claude --system-prompt "You are a security-focused code reviewer. Flag any potential security issues."
```

### Output Formatting

Control how Claude Code formats its output:

```bash
# JSON output for scripting
claude -p "list all exported functions" --output-format json

# Plain text without formatting
claude -p "summarize this file" --output-format text
```

### Network Configuration

For corporate environments with proxy requirements:

```bash
export HTTPS_PROXY=http://proxy.company.com:8080
export NO_PROXY=localhost,127.0.0.1
```

<Callout type="tip">
Create a `.claude/` directory in your project root even if you only need a single settings file. This directory is also where skills, hooks, and other Claude Code project-level configurations live. Adding it to version control ensures your entire team shares the same Claude Code setup.
</Callout>

## Configuration Checklist for New Projects

When setting up Claude Code for a new project, work through this checklist:

1. **Create CLAUDE.md** with project context, tech stack, and conventions
2. **Set up `.claude/settings.json`** with project-specific permissions
3. **Add relevant MCP servers** for databases, APIs, and services
4. **Create team skills** in `.claude/skills/` for common workflows
5. **Configure hooks** for quality gates and automation
6. **Document the setup** so team members can get started quickly
7. **Add `.claude/` to version control** (except for any files with secrets)

A well-configured Claude Code setup transforms it from a generic AI assistant into a team member that understands your project, follows your conventions, and respects your workflows. The initial investment in configuration pays dividends across every subsequent development session.
